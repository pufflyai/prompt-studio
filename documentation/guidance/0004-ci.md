# Pull requests and CI

## 1. Finishing a pull request

1. Develop with the [test-driven workflow](0005-testing.md#1-red-write-a-test-first). Run targeted tests while developing.
2. Push the branch and open a draft PR using the [Git rules](0007-contributing.md#1-git).
3. Before marking a behavioral PR ready, run the [targeted local review checks](../guides/development/0002-testing.md#targeted-local-review) with `bun run test:review --base origin/main`. The script must run at least every merge-queue test, even in unchanged packages: all fast repository/package P0, affected P1 source contracts, the canonical dashboard smoke, packaged desktop smoke and affected packaged flows. Queue tests cannot be deferred to CI or filtered by the diff. Include additional behavior tests with `--test <repository-relative-file>`. Target 15 minutes for routine changes, including setup and process cleanup. Broad changes must finish every selected check even when they exceed that target; do not truncate, skip, or queue them because of elapsed time. A full local suite is not required.
4. Routine copy, spacing, cosmetic, and documentation changes use [scoped verification](0005-testing.md#4-prove-it-works). They do not require the full test command or browser runs. Explicit user-requested validation still applies.
5. Before final validation, fetch `origin/main`. Integrate it only when the branch has merge conflicts with it or `git rev-list --count HEAD..origin/main` is greater than 10. This counts incoming commits, excluding commits only on the branch. Otherwise, leave `main` unmerged. After integration or repairs, recompute affected checks; rerun failed or affected checks without restarting unrelated passing suites.
6. For an unrelated failure, verify the failed test on `main` with a focused check. Find an open fix PR or open a separate one, then link it in this PR's description. Keep unrelated fixes out of this PR.
7. Run `gh pr ready` only when applicable CI is green on the latest commit, required local checks pass, and any explicitly required exceptional checks have passing evidence for that commit, except unrelated failures with a linked fix PR. The local report’s deferred inventory does not automatically require full native, packaged or benchmark matrices. An overrun, interrupted setup, missing coverage, or a local-only pass never waives this gate.
8. Read every review comment, including inline comments. Use `gh pr view <number> --comments` and `gh api repos/pufflyai/prompt-studio/pulls/<number>/comments`.
9. Fix valid review comments and reply to each comment. Batch the repairs, verify failed tests and affected behavior, and wait for CI on the consolidated commit. Do not require a final full local rerun.

10. Native, packaged and benchmark suites are expensive exceptions, not routine PR gates. Run them only for a concrete high-risk change that focused checks cannot establish, or an explicit user request. Record the risk and smallest complete owning workload before dispatch. A shared dependency change or deferred report entry alone is insufficient. Keep the normal PR workflow and targeted local review as the default; nightly and release validation retain their complete matrices.

11. Label PRs that change benchmarks, their workloads, fixtures, metrics, budgets, or runners `benchmark`. Before any merge action, read the current PR labels. Agents must not merge a `benchmark` PR, enable auto-merge, or add it to the merge queue. Leave review and merge to a human, even when CI is green. Do not remove the label to bypass this rule.

## 2. CI completion

1. After every push, wait for all applicable checks on that commit to finish.
2. Inspect all failures from the current run and fix their causes as one batch. Verify the failed set locally before pushing the consolidated repair. Avoid one push or full workflow rerun per finding; normal latest-head CI still applies.
3. Pending, failed, cancelled, or timed-out required checks mean work is unfinished. Preserve outcomes from optional diagnostics separately; do not describe them as passing or silently promote them into routine PR gates. Checks skipped by workflow conditions are allowed.
4. Passing local checks or opening a draft PR does not complete the task.
5. If CI is blocked, report the blocker and keep the PR open. Do not report the task as done.
6. If `published_extensions` fails only because an extension needs unpublished SDK or UI changes, add `waiting-for-release` and report the release blocker. Do not work around the check. See [PR labels](../guides/development/0004-pull-request-labels.md).

## 3. CI timeouts and performance budgets

1. A performance budget is a product contract for one named operation and fixed workload. Benchmarks own budgets. A failed budget is a slowdown to fix.
2. An execution allowance, or timeout, bounds the whole test, fixture, or job, including setup and cleanup. When it expires, find the slow phase first. See [ADR 0067](../adrs/0067-separate-performance-budgets-from-execution-allowances.md).
3. Never increase a budget or timeout without clear approval for that exact value in the same conversation, even if it is the only way to pass a check.
4. Approval covers benchmark budgets, workflow `timeout-minutes`, Playwright `timeout`, `expect.timeout`, and `webServer.timeout`, and whole-test or fixture limits such as `test.slow()`, `test.setTimeout()`, and fixture `timeout`.
5. Never pass a budget by shrinking its workload, skipping a platform, retrying, or prewarming a cold-start scenario.
6. If a check times out, report which phase was slow and by how much.
7. Before proposing a timeout, collect representative local and applicable CI-platform timings as described in the [testing guide](../guides/development/0002-testing.md#time-limits). Local evidence alone or CI evidence alone is insufficient. Fix the slowdown or ask the user what to do.
