# Docker test workspaces

This setup stays in the owning extension under [RB 1.A.3](../../requirement-book/book.json). The Remote Testing companion owns the test image extension, Git transfer and operator admission sources. Use this setup for trusted repository tests. Keep provider configuration, certificates, manifests with operator values and build output outside Git. No host Docker socket, node filesystem mount, cloud credential or shared daemon enters a workspace.

## Runtime and lifecycle

Build `extensions/remote-testing/runtime/Dockerfile` from the repository root with `WORKSPACE_IMAGE` set to the deployment's approved, digest-pinned PocketCoder test runner. It preserves that image's supervisor and runtime descriptor and replaces its Pi test process. The image adds the repository-pinned Node runtime, Docker CLI, Compose and Buildx; render a new immutable template using the resulting image digest. The supervisor digest remains unchanged.

`extensions/remote-testing/operator/docker-admission.ts` runs as an operator-owned TLS admission service. An exact image allowlist selects equipped test Pods; other images never receive Docker. Image-evidence probe Pods for an approved runtime receive only the trusted-pool scheduling and tolerations needed to inspect the same node; they retain their original unprivileged security. The service requires a controller-owned workspace Job, a writable workspace mount and native Linux execution. It moves selected Pods to a dedicated, tainted trusted-test node pool and adds one privileged Docker daemon as a native sidecar. The runner and daemon mount the same `/workspace` at the same path, including temporary review checkouts, so bind mounts and published localhost ports work. The Unix socket is private to that workspace. There is no TCP Docker API. Docker data has a separate bounded, disposable volume.

A startup probe waits for `docker info` before the workspace starts. Native sidecars stop after the main workspace container, including Job failures and cancellation; deleting the Pod removes its daemon, containers, image cache and volumes. Companion collection still owns normal workspace shutdown. Check the saved workspace ID after every run.

Docker access permits privileged code on its worker node. These workspaces are for trusted project code only. The trusted-test pool must be separate from system services and untrusted workloads, use a minimal node identity, and carry `pocketcoder.dev/trusted-tests=true:NoSchedule`. The admission service itself runs unprivileged on the system pool with no service account token. Keep the allowlist and its namespace under operator control. Never add an image for untrusted uploads. This does not change the general workspace security contract.

## Deploy

1. Provision a native Linux trusted-test node pool labeled `pocketcoder.dev/pool=trusted-tests`, with the taint above. Use at least 8 CPUs, 16 GiB RAM and enough ephemeral disk for the declared workspace and Docker volumes per scheduled run. Enable autoscaling to zero. Reserve additional capacity for concurrent runs; never repurpose another run's worker.
2. Build the runtime image on the cloud builder and retain its digest. Choose a compatible, digest-pinned `docker:dind` image. Use the same Docker major for client and daemon.
3. Bundle `docker-admission.ts` with `bun build extensions/remote-testing/operator/docker-admission.ts --target bun --outfile /private/build/docker-admission.js`. Install it in ConfigMap `remote-test-docker-code`. Create a TLS key and certificate for `remote-test-docker.<namespace>.svc`, with a finite expiry, and install Secret `remote-test-docker-tls`. Retain the CA certificate for the webhook; rotate certificate, Secret and CA before expiry.
4. Supply a private JSON config to `docker-deployment.ts`: `namespace`, `image` (the TLS service's approved Bun image), `images` (equipped test image digests), `daemonImage`, `nodeSelector` (the trusted pool label) and base64 `caBundle`. Render with `bun extensions/remote-testing/operator/docker-deployment.ts /private/config.json > /private/deployment.json`. Apply the ConfigMap, Deployment, Service and NetworkPolicy first. Wait for healthy endpoints before installing the MutatingWebhookConfiguration. Its fail-closed match condition selects only approved test images. Permit control-plane access to the webhook's port 8443 through the cluster firewall.
5. Run `bun extensions/remote-testing/operator/prepare-test-template.ts /private/tests.json <image@digest> /private/equipped-tests.json`. It preserves operator services and runtime pins while increasing workspace storage and producing a new version. Repeat for a preview base when previews should also have Docker. Keep the base names `remote-tests` and `prompt-studio-preview`. Publish the approved branch families, replace the companion's private approved bases and select the new default test version. Preserve old immutable templates and running workspaces.
6. Install the matching companion through `pst extensions add /absolute/extensions/remote-testing --force`. Install Cloud Workspaces similarly when its skills changed. Preserve global connections and project settings.

## Qualification

Run a new workspace through the companion. Check `docker info`, `docker compose version`, `git rev-parse HEAD`, `git merge-base origin/main HEAD`, and a container with a bind mount from the workspace and a dynamically published port. Verify that the exact committed candidate remains HEAD; dirty uploads must preserve their base as a parent. Run the intended `test:review` selection and keep its full log and required desktop CI evidence. Inspect the matching Pod for the approved sidecar and trusted pool. After collection, verify that the Pod and daemon disappeared while unrelated workspaces remain running.

Uploads include candidate and comparison-base Git history and refs, so review historical content as well as current files before upload. Host Git configuration, hooks and linked-worktree pointers are never copied. Fetch the intended base on the host first; an absent base or shallow source must be repaired before review. A clean exact-commit run retains that commit; an edited working tree receives a new child commit in the runner.

Source history covers the selected candidate and comparison base, with refs pointing into those histories. The default base is `origin/main` (then local `main` or `master` when available). Choose a named branch, tag, custom ref or commit SHA; resolve HEAD-relative expressions to a SHA on the host. Pass `--base <ref>` to the remote command for another comparison base, and use the same base in `test:review`. Fetch it on the host before upload. Unrelated workspace branch histories stay on the host.
