# 10. Data Renderer And Favorites

A data renderer is a Notion/Linear-style data workspace registered as a
renderer kind. The contribution provides:

- **Schema** — `tagDefinitions`, `groupingOptions`, `orderingOptions`,
  `displayPropertyOptions`, `filterCategories`.
- **Data** — `executeQuery(state)` receives current `{ settings, filters }` so a
  backend can push filter/sort/pagination down. The built-in
  `<DataRenderer>` re-applies filter/sort/group locally, so simple
  implementations can return all rows and let the workspace filter in memory.
- **Row mutations** — `onTicketClick`, `onMoveTicket`, `onTagChange`, etc.
- **Optional `savedViews`** — `{ resourceKind, scope, projectId? }`. When set,
  the workbench renders a `SavedViewMenu` in the workspace toolbar wired to
  `workbench.savedViews.{create, update, rename, duplicate, delete}`.

`renderers.registerDataRenderer({ id, ... })` auto-registers a widget renderer
with the same id; placement is a regular `layout.registerWidget` call.

**Saved-view application is loose-coupled**: the data renderer never imports
the saved-view registry. When a saved-view resource is opened in this widget,
`WorkbenchDataView` reads `placement.resource.metadata.{filter, display}` and
applies it to the per-placement workspace store. Saving back goes through the
SavedViewMenu callbacks, which call the registry on the data renderer's behalf.

**Favorites** are a separate scoped registry — `favorites.add({ target, scope,
projectId? })` stores a `ResourceRef`. The left tree in this story has two
sections: one backed by `favorites.list(...)`, one by `savedViews.list(...)`.
Toggling a saved view as a favorite makes it appear in the first section
without re-creating the resource.

Per-placement state isolation: the workspace's storage key is derived from the
placement (`pstdio:workbench:savedView:<viewId>` when a saved view is open,
otherwise `pstdio:workbench:dataRenderer:<rendererId>:<widgetId>`). Two open
saved views never share their filter/display state.
