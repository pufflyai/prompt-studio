# 14. Locations, Panels, Sub Panels, and Panel Menus

The Workbench uses one domain-neutral hierarchy. A navigated Location is the active Panel; Main, Secondary, and Side
are the surfaces through which that Panel presents its workspace:

```text
Breadcrumb
└── Location Panel
    ├── fixed Location content
    ├── Main / Secondary / Side surfaces
    │   └── tabbed Sub Panels
    └── left/right Panel Menus
        ├── owned by the Location Panel
        └── or owned by one Sub Panel
```

A **Location Panel** is the navigated subject represented by the breadcrumb. Its content renders directly while no
Sub Panels are open. Once a Sub Panel opens, the Location Panel becomes the first, uncloseable tab so the user can
select its content again. A **Sub Panel** is removable tabbed content inside that Location Panel. A **Panel Menu** is
supporting content attached to either the Location Panel or one specific Sub Panel; it never becomes a tab or an
Add-panel entry.

## Registration and ownership

Native Workbench modules declare menus on the Panel that owns them. The registration derives the left/right region,
records the exact owner contribution, opens the menus with the Panel, and disposes them with the Panel. A reusable
Panel factory therefore carries its menus everywhere that Panel is registered; there is no separate owner ID to keep
in sync.

```ts
const notesMenus = (prefix: string) => [
  {
    id: `${prefix}.tools`,
    title: "Notes tools",
    icon: "FileText",
    side: "right" as const,
    rendererId: "notes.tools.renderer",
  },
];

ctx.layout.registerLocation({
  id: "notes.location",
  title: "Notes",
  region: "main",
  rendererId: "notes.renderer",
  panelMenus: notesMenus("notes.location"),
});

ctx.layout.registerSubPanel({
  id: "notes.secondary",
  title: "Notes",
  region: "secondary",
  rendererId: "notes.renderer",
  panelMenus: notesMenus("notes.secondary"),
});
```

`registerPanelMenu` is the lower-level integration seam used by the extension adapter for independently declared
`panel-menu` roles. Native modules should prefer ownership through `panelMenus`.

## Header and ownership rules

The Panel Header is shown when the Panel has at least one open Sub Panel, one eligible closed Sub Panel, one attached
or collapsed Panel Menu, or a header action. When Sub Panels are open, the tab strip begins with the uncloseable
Location Panel and continues with the removable Sub Panels. `Add panel` renders only when an eligible closed Sub Panel
exists. Therefore a Location with no subordinate UI has no header, while a Panel containing only a Panel Menu retains
its header without emitting an empty ARIA tab list.

Sub Panels and Panel Menus can declare Location eligibility by mode, resource kind, resource id, or an
`eligibleLocations.canOpen` predicate. Resource-backed Sub Panels validate their own resource separately from this
Location eligibility. Menu ownership is exclusive to the selected tab: selecting the Location Panel shows only
Location-owned menus, while selecting a Sub Panel shows only that Sub Panel's menus. Each menu placement retains its
own attached or collapsed state. Clicking a collapsed menu's distinct, tooltipped icon opens the menu's live content
in a contained, portal-positioned dropdown. Its header identifies the menu and contains the action that attaches it to
the correct side again. Attach is disabled when the Panel cannot preserve the menu minimum, resize handles, existing
attached menus, and minimum content width.

Each Location owns its open Sub Panel placements and selection. Switching Locations does not close those tabs:
returning by a Location action, Back, or Forward restores that Location's previous open tabs and active selection.
Contributions that are not eligible for the active Location remain out of its tabs, Add-panel menu, and menu layout.
Every Sub Panel offered by `Add panel` is removable and becomes eligible again after closing.

A Location or selected Sub Panel can set `floatingPanels: "hidden"` when floating Panel chrome would cover important
content. This suppresses both the floating Panel and its recovery bubble without changing the saved Panel mode;
attached recovery controls remain available when that Location still has eligible or open subordinate content.

## Navigation and persistence

Selecting the Location Panel or a Sub Panel in Main, Secondary, or Side records one navigation entry. The entry
snapshots the Location and the selected Sub Panel, if any, in every Panel. Back and Forward replay the complete
snapshot without adding another entry;
navigating after Back truncates Forward entries. Closing a Sub Panel removes its selection from older snapshots so
history cannot recreate it implicitly.

The project-scoped persistence record contains the ordered entries, cursor, recently closed entries, and schema
version. Layout persistence retains open Sub Panel placements, active Location, region visibility and sizes, and Panel
Menu placement, collapsed state, and size. On reload, the host waits for native and extension contributions, removes
missing Locations, clears unavailable Sub Panel selections, compacts adjacent equivalent entries, clamps the cursor,
and restores the cursor entry atomically. Forward entries remain available when reload occurs from the middle of the
timeline.

## Extension roles

Extension views declare their relationship explicitly:

```ts
views: {
  overview: {
    title: "Overview",
    role: "location",
    webview: { entry: packageAsset("./overview.tsx", import.meta.url) },
  },
  report: {
    title: "Report",
    role: "sub-panel",
    target: "workbench.secondary",
    webview: { entry: packageAsset("./report.tsx", import.meta.url) },
  },
  inspector: {
    title: "Inspector",
    role: "panel-menu",
    target: "workbench.main.right",
    panelMenuOwner: { level: "panel" },
    controlsRenderer: "inspectorControls",
  },
  reportTools: {
    title: "Report tools",
    role: "panel-menu",
    target: "workbench.secondary.right",
    panelMenuOwner: { level: "sub-panel", view: "report" },
    controlsRenderer: "reportToolsControls",
  },
  createItem: {
    title: "New item",
    role: "modal",
    webview: { entry: packageAsset("./create-item.tsx", import.meta.url) },
  },
}
```

Product concepts stay outside `@pstdio/workbench`: a host decides which routes are Locations, which resource-owned
views are Sub Panels, and which attached tools are Panel Menus. For example, a dashboard can bind a Properties controls
renderer to a ticket Location as an anonymous generic Panel Menu without adding ticket or planner logic to Workbench.
