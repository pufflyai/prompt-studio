# 14. Declare settings that features can read

A preference is a named setting. A feature reads the setting by name instead of owning a separate settings store.

The schema declares four facts in one place:

- the preference name
- the value type and allowed choices
- the default value
- where the selected value is saved

The settings UI uses that schema to build controls. Feature code reads the selected value from the preference registry.
Both use the same definition, so they cannot disagree about the name, default, or scope.

Try the example in this order:

1. Change **Editor density**. The spacing in **Editor preview** changes.
2. Change **Default open region**. The selected region changes under **New resources open in**.
3. Compare the scope badges. Density follows the user everywhere. The open region belongs only to this project.

## When to use this

Use a preference for a choice that must survive after the current panel closes, such as density, a default location, or
a feature option. Component state is still the right place for temporary UI state.

This is the Core API used by an application that embeds the workbench. An extension declares the same kind of setting
under `settings` in `defineExtension`. The host converts that extension definition into a preference schema.

## What each field means

The schema declares the contract for each preference:

- `properties` maps each preference name to its schema entry. The name is the stable identity feature code reads.
- `type` is the value type, here `"string"`.
- `enum` lists the allowed choices.
- `default` is the value used before anyone picks one.
- `scope` says where a choice is saved: `"user"` values follow the user everywhere, while `"project"` values belong to
  one Prompt Studio project.
- `description` explains the preference to readers of the schema and to settings UI.

Scope references select which saved value an operation targets:

- `{ scope: "user" }` targets the user's own value.
- `{ scope: "project", scopeId }` targets one project's value. `scopeId` names that project.

The module registers the schema and a panel that uses it:

- `ctx.preferences.registerSchema(...)` publishes the schema so the settings UI and feature code share one
  definition.
- `ctx.views.registerView(...)` defines the demo panel. `body.kind: "react"` lets host code render React, and
  `render` receives the render input for one visible placement.
- `ctx.shellPlacements.registerPlacement(...)` places the View. `item.kind: "view"` places one static View,
  `item.view` names it, `item.presence: "fixed"` keeps it open without a close button, and `region: "main"` picks
  the region.

The panel reads and writes values through the preference registry:

- `input.workbench.preferences.getValue(name, scope)` returns the value saved for that scope, or the schema default.
- `input.workbench.preferences.setValue(name, value, scope)` saves a new value for that scope.
- `useWorkbenchStore(input.workbench.preferences.store, selector)` subscribes to registry state. The example selects
  `state.schemas` to list the registered entries.
