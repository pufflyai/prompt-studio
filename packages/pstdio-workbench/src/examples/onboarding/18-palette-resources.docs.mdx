# Add actions to resource menus

Resource menus expose commands for one resource kind. The primary slot holds common actions. The context slot holds the
full right-click menu. Both invoke registered commands with the active resource context.

## What each field means

`defineResourceKind(...)` declares one kind of domain object:

- `id` is the stable kind identity inside the extension.
- `label` is the user-facing name.
- `menuSlots` lists the menu areas this kind owns. Each slot is a named place where commands can appear.

Each menu slot entry:

- `id` names the slot. Commands target the slot by this name.
- `placement` picks the built-in menu area: `"header-primary"` for common header actions, `"header-overflow"` for the
  header's overflow menu, or `"context-menu"` for the right-click menu.
- `access` controls who may contribute. `"owner"` accepts commands only from the extension that declares the kind.
  `"public"` also accepts commands from other extensions.

`defineCommand(...)` declares the action:

- `id` is the stable command identity.
- `title` is the command's user-facing name, shown in surfaces such as the command palette.
- `menus` lists where the command appears. Each entry targets one slot.
- `run(ctx)` executes the command. `ctx.resource` carries the resource the menu was opened on, so the handler knows
  which ticket to act on.

Each menu entry:

- `slot` is the target, built with `resourceMenuSlotRef(kindRef, slotId)`. The helper pairs a resource kind reference
  with one of its slot ids.
- `label` is the text shown in the menu.
- `presentation` picks how the entry renders: a `"button"`, an `"icon-button"`, or a `"menu-item"` row.

`defineExtension({ resourceKinds, commands })` packages the contributions. The host resolves each menu entry against
the declared slots. An entry that targets an unknown slot stays visible as an unresolved diagnostic instead of failing
silently.
