# 13. Add host settings

This Core API example adds settings owned by the host application. A section groups related entries. A panel supplies
either a preference schema, a custom editor, or a collection-backed editor. The example registers all three panel
kinds, then opens the settings overlay on the Appearance panel.

Choose global or project scope based on who owns the value. The host resolves the active scope; the extension should
not copy project identity into its settings UI.

## What each field means

The module declares the data the settings surface renders:

- `ctx.preferences.registerSchema(...)` registers the named preferences the schema panels edit. Each schema entry
  declares the value type, allowed choices, default, and scope.
- `ctx.settings.registerSection({ id, title, order })` adds one group in the settings tree. `order` sorts sections;
  lower values sort first. Panels join a section through their `section` field.

`ctx.settings.registerPanel(...)` adds one settings page. The `kind` field selects how it renders:

- `kind: "schema"` auto-generates controls from registered preferences. `preferences` lists each entry as a
  preference `name` plus a user-facing `label`.
- `kind: "view"` renders a registered View instead of generated controls. `viewId` names that View. Use it only when
  the shared controls cannot represent the setting.
- `kind: "collection"` renders one tree node per item and opens an item editor View when the user selects a node.

Fields shared by every panel kind:

- `id` is the stable panel identity inside the settings surface.
- `title` is the label shown in the settings tree.
- `section` places the panel under a registered section.
- `scope` says who owns the values: `"global"` values follow the user, `"project"` values belong to one project.
- `icon` names the icon shown next to the panel title.
- `description` is short helper text shown on the panel.
- `save: "apply"` stages edits behind an explicit Save action. Without it, edits save live.

Fields specific to the collection panel:

- `viewId` names the View that edits one selected item.
- `items` returns the current items.
- `itemId` and `itemLabel` derive each tree node's identity and label from an item.
- `groupBy` groups nodes: `key` picks the group for an item, `order` sorts the groups, and `label` names them.
- `actions` adds toolbar actions such as Create. Each action has an `id`, `label`, `icon`, and `run` callback.
- `ctx.settings.refresh()` tells the surface to re-read `items` after data changes.

The item editor View reads its subject from the render input:

- `input.instance.resource?.metadata` carries the `panelId` and `itemId` of the selected collection node.
- `input.workbench.settings.getCollectionItem(panelId, itemId)` returns the matching item.

The host wiring around the panels:

- `createWorkbenchSettingsModule({ resolveScopeId })` activates the unified settings surface: the tree, the
  dispatching panel, and the presenter. `resolveScopeId` maps a scope to a storage key, so project entries appear
  only when a project scope id resolves.
- `ctx.shellPlacements.registerPlacement(...)` with `presence: "fixed"` keeps a launcher View in the `main` region.
  The settings surface is a modal overlay, so the launcher gives the user a way back in after closing it.
- `ctx.commands.executeCommand(WORKBENCH_SETTINGS_OPEN_COMMAND_ID, { panelId })` opens the overlay on one panel.
