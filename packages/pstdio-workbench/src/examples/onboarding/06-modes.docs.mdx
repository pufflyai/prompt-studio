# 7. Compose a mode with a page

This is the Core API representation that the validated Extension API compiles into.

A mode contributes context that stays while related pages change. A page contributes content for one location. This
example uses a release project, its tickets, and an active coding session so each owner has visible work to do.

Try these transitions in the story:

1. Start on Project overview. The Sidenav contains **Northstar project** navigation.
   The page's release summary appears in Secondary.
2. Open Tickets. Northstar navigation stays, while Secondary shows the ticket filter.
3. Open the current session. Both project contributions disappear. **Session S-104** navigation and session context
   replace them.
4. Use Back and Forward. The workbench restores the complete mode and page composition for each location.

## What each field means

The outer setup prepares the workbench:

- `createWorkbench({ startPage })` creates the service container and names the page to open first.
- `workbench.modes.registerMode(...)` declares each mode. `id` is the mode identity, `label` is its user-facing name,
  and `activate` runs when the mode becomes active. This example needs no activation work.
- `workbench.pageLocations.switchProject(...)` selects the active project. Navigation needs an active project before
  it can commit a page location.

`registerModeSidenav` contributes the mode-owned navigation:

- the tree View uses `body.kind: "tree"`. `defaultExpandedSectionIds` lists the sections that start expanded.
  `getBody` returns one section with an `id`, a `label`, and its `nodes`. Each node has an `id`, a `label`, and a
  page `target`, the NavigationTarget `{ kind: "page", page }`. The project tree lists Overview and Tickets. The
  session tree lists only the current session. `getChildren` returns an empty list because each tree is flat.
- `workbench.modePlacements.registerPlacement(...)` places the tree. `id` is the registration identity. `ref` is the
  public placement reference. `modeId` names the owning mode, so the placement appears only while that mode is active
  and is removed when the mode changes. `item.kind: "view"` with `item.view` renders one static View.
  `item.presence: "fixed"` keeps it open while the mode is active; the user cannot close it. `region: "sidenav"` and
  `movableTo: ["sidenav"]` keep it in the Sidenav.

`registerPage` contributes each page and the Views it renders:

- the main View uses `body.kind: "react"`. Its `render` receives the render input, and `input.workbench` exposes the
  core services. The buttons call `input.workbench.pageLocations.navigate({ kind: "page", page })` to open another
  page and commit one canonical location.
- the tools View is a second React View that renders the page-owned content in Secondary.
- `workbench.pages.registerPage(...)` registers the page. `id` is the registration identity. `ref` is the public page
  reference that navigation targets use. `title` is the page name. `path` is the URL path segment. `modeId` names the
  owning mode, so opening the page also activates that mode.
- `main: { kind: "view", view, cardinality: "one" }` renders the page content.
- `slots` contains the page's Secondary panel with `region: "secondary"` and
  `item: { kind: "view", view, presence: "open" }`. It starts open and the user may close it.
  Saved user choices apply on the next visit.

Shared mode placements keep their identity across pages within the mode. Page panels belong to their page location.
Removing an owning contribution disposes its instances.

This host example registers its Sidenav through the Core API. Extension authors contribute sidebar content through
`navigationItems` and `navigationTrees`, or replace it with `mode.chrome.sidenav`. Extension page slots and mode
placements use Main, Side, and Secondary.
